# iPhone 4S (n94ap, A5 / S5L8940X): `-M iPhone-4S`

The project's target board: iOS 6.1.3 (10B329) on the A5, booted from a kernel bundle (kboot) with no
boot ROM or iBoot, as the A4 boards in `hw/arm/ipad1.c` are. The hardware as the IPSW describes it is
in `hardware.md`; the raw inventory (`devicetree.txt`, `iomap.tsv`, `kexts.txt`) is regenerated by
`ios-prep`.

## Preparing the firmware

Apple's `iPhone4,1_6.1.3_10B329_Restore.ipsw` (SHA-256 601d5112...56d2, 965,016,471 bytes) and the
keys on The Apple Wiki (`Keys:BrightonMaps_10B329_(iPhone4,1)`; `ios-prep` fetches them, or pass
`--keys`). From the repository root, with Python 3 and `cryptography`:

```
python tools/ios-prep/ios_prep.py prepare ../firmware/iPhone4,1_6.1.3_10B329_Restore.ipsw \
    --out ../firmware/n94_10B329 --docs docs/n94
```

Output (`hashes.json` records every SHA-256):

| File | What | Check |
|---|---|---|
| `kernelcache.mach` | 14,053,376 B | `feedface`, armv7, `xnu-2107.7.55.2.2~1/RELEASE_ARM_S5L8940X`, Adler-32 of the complzss verified |
| `DeviceTree.bin` | 78,520 B | first property `compatible` = `N94AP`, `iPhone4,1`, `AppleARM`; 101 nodes |
| `iBoot.bin`, `LLB.bin`, `AppleLogo.bin` | decrypted stages and the boot logo | `iBoot-1537.9.55` string, `iBootIm` header |
| `rootfs.hfs` | 1,279,774,720 B | HFSX (`HX`) volume header at 0x400, journaled |
| `kboot.bin` | 14,405,656 B | `K48KBOOT` trailer: load 0x80000000, entry 0x800860c8, boot_args 0x80DBC000 |
| `identity.json` | the synthesized unit (serial, MLB, ECID, MACs), seeded | reproducible with `--seed` |

What the bundle holds (`kboot.json`): the kernel's segments at their link addresses (VA == PA on the
A5 with no slide), the filled device tree at 0x80DA8000 and a boot_args page at 0x80DBC000 with
**Version 18**, which is what this kernel's `pe_identify_machine` compares against (the A4 6.x
kernels want 3; `ios-prep` reads the value off each kernel). `memSize` is 512 MiB minus vram and
pram, `topOfKernelData` 0x80DBD000 rounded to 16 KiB. The device tree gets the iBoot fills the A4
boards get (identity, flags, clocks, memory map, sgx unmatched, test IMEI; the NVRAM proxy image only
without `--nand ppn`, since with the NVRAM on the NAND the kernel must read it from IOFlashNVRAM) plus:

- `--cpus 1` (default for bring-up): `cpus/cpu1` is unmatched (`device_type off`, name `xcpu`).
- `--nand raw` (default): the A4 raw-NAND geometry and `ppn-device 0`; `--nand ppn` keeps PPN.
- `--hide NODE` unmatches any further node; `--verbose-boot` appends `-v`.
- `--ramdisk restore|update` (with `--ipsw` once, to decrypt it) stages the IPSW's ramdisk after boot_args,
  under topOfKernelData, publishes it as `chosen/memory-map/RAMDisk` and adds `rd=md0`: the kernel's md
  driver makes it the root, as iBoot does for a restore. That is how M2 was reached without a NAND model.
- `--cpus 1` also puts `cpus=1` in the boot-args: AppleARMPE counts every child of `/cpus` (the hidden
  cpu1 included) for the CPU interrupt controller and only that boot-arg lowers the count; with 2 expected,
  `AppleInterruptController::start` blocks in `IOCPUInterruptController::registerInterrupt` forever and no
  device interrupt is ever unmasked.

`prepare` also makes the system-volume edits that every unit needs. These are per firmware, so every
device made from this IPSW shares them. Each edit is idempotent, and an image that already has an edit
is not opened for writing:

- lockdownd's activation short-circuit ("Activation" below; `--stock-lockdownd` leaves it out).
- The M3 launchd edits, `sysvol.UNIT_EDITS` (`--stock-jobs` leaves them out): `CA_ENABLE_OGL=0` for
  backboardd and SpringBoard, and BTServer and BlueTool disabled.

## Virtual devices: IPSW to a usable unit in one command

`ios_prep.py device` chains the flow of B1-B4, M3 and Activation below, so there are no hand-run steps.
A *device* is a directory with its own PPN page store, a storage size chosen at creation, a random
identity seed (serial, ECID, MACs), and kboot bundles built for that store's geometry. The firmware
directory is shared: every device made from one IPSW serves the same `rootfs.hfs` read-only through marker
pages, so a device costs only the pages it writes. From the workspace root (the folder holding `iPhonEmu/`,
`firmware/` and the `.venv`):

```
python iPhonEmu/tools/ios-prep/ios_prep.py device create meu4s --ipsw firmware/iPhone4,1_6.1.3_10B329_Restore.ipsw --storage 16G
python iPhonEmu/tools/ios-prep/ios_prep.py device boot meu4s            # SDL window, QMP on 4444/4445
python iPhonEmu/tools/ios-prep/ios_prep.py device list
python iPhonEmu/tools/ios-prep/ios_prep.py device delete meu4s          # asks; --yes does not
```

`--root DIR` (or `IPHONEMU_DEVICES`) says where the devices live. The default is `devices/` beside the
repository. Each command takes it.

`device create NAME --ipsw IPSW [--storage 16G] [--firmware DIR]`:

1. **Firmware.** Uses `firmware/<board>_<build>` beside the repository (`n94_10B329`), or `--firmware`.
   If that directory is not prepared, it runs `prepare` (edits included). If it is prepared, the command
   checks it against the IPSW's SHA-256 (`hashes.json`) and applies any per-firmware edits it lacks.
2. **Store.** `<root>/NAME/nand`, of `--storage` raw size: 2, 4, 8, 16, 32 or 64 GiB (default 16G; the
   4S was sold with 16, 32 and 64 GB, and 8 GB came in 2013). The size scales the blocks per CAU
   (`nand_ppn.geometry`: 2048 at 8 GiB, block_bits to match), with the same two chips and the same
   partition table layout. The chip files are sparse and grow as the guest writes.
3. **Install boot.** `install` for this store (helpers, markers, install ramdisk, the factory data ark),
   a bundle with this store's geometry and the device's identity (install ramdisk as root,
   `nand-enable-reformat=1`, AE2 hidden), and QEMU until `it_install: done`. QEMU is then quit through
   the monitor on a stdin pipe, as `run-install.sh` did. `FAIL`, a kernel panic or the time limit (`--limit`,
   default 1200 s + 150 s per GiB) marks the device `failed` and points at its serial log.
4. **Normal bundle.** `<root>/NAME/kboot.bin`, the same geometry and identity, AE2 shown. `device.json`
   says `ready`.

`device boot NAME [--display sdl|none] [--qmp PORT] [--detach] [-- QEMU ARGS]` runs `-M
iPhone-4S,kboot=<dev>/kboot.bin,nand=<dev>/nand`, with the serial log in `<dev>/logs/serial.log`. It
opens QMP on PORT and PORT+1 for `tools/dev/n94_input.py --port`, as `run-m4.sh` does. On the devices measured below, the first boot showed Setup's welcome screen within 4 minutes (M3's
first boot had a 14-minute data migration first). Setup goes on to the home screen with no activation
page ("Activation").

`device refresh NAME` repeats the install boot on an installed store. The markers are written again and
the data volume and keybag are kept. A device needs this after a later edit to its firmware's
`rootfs.hfs`, because the FTL's garbage collection copies served pages and those copies do not follow
the edit ("M3", item 4).

`device delete NAME` removes `<root>/NAME` and nothing else: the directory must hold a `device.json`
and sit directly under the root. The firmware stays for the other devices.

Two devices coexist. They have different stores and identities and use the same firmware directory, and
they can run at the same time if their QMP ports differ. Each running QEMU holds `<dev>/qemu.lock` with
its PID. `boot`, `refresh` and `delete` refuse a device whose QEMU is alive. That enforces one QEMU per
store, which the page files' own locking does not on Windows.

Layout of `<root>/NAME`: `device.json` (firmware, IPSW, size, seed, state, install history), `nand/`
(`geometry.json`, `ch*-ce0.pages`, `markers.json`, with an absolute `rootfs.hfs` path when the store is
on another drive), `install/` (`it_install`, `it_keybag`, `ramdisk-install.dmg`, `kboot.bin`),
`kboot.bin` with its `.json`, `identity.json`, `logs/`. Lower-level commands for a store of another size:
`nand --out DIR --storage 4G`, then `kboot ... --nand ppn --nand-store DIR`.

Measured on 2026-10-18 (stores on E:, firmware on C:, two `create` runs in parallel):

| | 4 GiB device (`t4`) | 16 GiB device (`t16`) |
|---|---|---|
| FTL block device | 976,563 sectors | 3,906,250 sectors |
| Install boot | 63-72 s (a blank store formats in seconds) | 88 s |
| On the host | 1.5 GB (the marker pages are whole pages) | 1.5 GB |

Both then booted at the same time (`--qmp 4544` and `--qmp 4644`, `--display none`). Each showed Setup's
welcome screen ("iPhone", slide to set up) within 4 minutes, auto-locking until a Home press. With both
running, `device delete t4` and a second `device boot t4` were refused. `device refresh t4` took 185 s
("already installed", the system keybag left as it was), and `device delete t4 --yes` removed only
`t4`. Setup was not walked to the home screen on these devices. The activation patch they get is the one
M4 walked, on the same firmware directory.

Not automated yet:

- Only the iPhone 4S (n94ap) on 10B329 has been walked. `create` refuses other boards. Another 4S build
  would need its own keys, and possibly lockdownd patch sites and launchd edits of its own.
- Setup Assistant is walked by hand, by mouse in the SDL window or `n94_input.py`: language, country,
  Location Services, set up as new, Apple ID skipped, terms, diagnostics.
- The first boot and Setup happen at the first `device boot`, not in `create`.
- QEMU must already be built (`build/qemu-system-arm`). On Windows the MSYS2 UCRT64 DLLs come from the
  workspace's `toolchain/msys64/ucrt64/bin`.
- The install helpers need clang and ld.lld (UCRT64's are found; `--clang`/`--lld` otherwise).
- Nothing reaches the network, Wi-Fi or Bluetooth (no models). These were already missing before this
  command.
- No snapshot or reset of a device's data volume short of `delete` + `create`.
- The future `iPhonEmu.exe` front end (phase 7) is not written. It would call these commands.

## Booting

From the repository root (the Windows build is `build/qemu-system-arm.exe`, run from the MSYS2 UCRT64
shell so its DLLs resolve):

```
build/qemu-system-arm -M iPhone-4S,kboot=../firmware/n94_10B329/kboot.bin -serial stdio -display none \
    -d unimp,guest_errors -D ../runs/n94/m1.log
```

`-trace 's5l8940_aic*'` logs every AIC access (the timer and FIQ included). For a bounded run whose
qemu log is flushed, quit through the monitor instead of killing the process:
`(sleep 150; echo quit) | build/qemu-system-arm ... -serial file:../runs/n94/m1-serial.log -monitor stdio`
(`runs/n94/run-m1.sh`, outside the repository, does this). Note that `-trace file=` also receives the
`-d` log output.

### M2: launchd from the restore ramdisk (2026-10-17, `runs/n94/m2-serial.log`)

```
python tools/ios-prep/ios_prep.py kboot ../firmware/n94_10B329 --ramdisk restore \
    --ipsw ../firmware/iPhone4,1_6.1.3_10B329_Restore.ipsw --hide arm-io/iop --hide arm-io/ae2
build/qemu-system-arm -M iPhone-4S,kboot=../firmware/n94_10B329/kboot.bin -serial stdio -display none
```

The two IOP nodes are hidden because `AppleA5IOP` and `A5AE2` load their EmbeddedIOP firmware and wait for
the coprocessor forever (the IOP core model is M3 work with the NAND). What happens, in order:

- `AppleInterruptController` registers (it needs `cpus=1`, above), so drivers get their interrupts: the
  watchdog, the serial ports, the light sensor, DWI, the CDMA with its AES filter.
- `CDMAAES` starts the `IOAESAccelerator`, which asks the platform for `SecureRoot`; AppleARMPE answers once
  bsd_init has named the root (`secure-root-prefix` is `md`, so `md0` is secure) and that handshake is what
  releases `IOSecureBSDRoot` in bsd_init. Without the CDMA the kernel sat forever after `BSD root: md0`.
- The PMU driver finds the D1881 on i2c0 (events, ADC, RTC counter and restart modeled; the ADC reads
  mid-scale on every channel), the compass and accelerometer start, the gyro fails its calibration check;
  `BSD root: md0`. restored's log carries the host's date.
- `launchd[1] has started up`; `restored_external` runs, finds no display service and no USB host
  (`enable_usb_connections failed`), waits in vain for the `IONVRAM` resource (the NVRAM lives in the NAND's
  partitions on this board) and exits asking for a reboot.
- The USB stack comes up on the A4 models (PHY, Synopsys OTG in device mode with its built-in host, EHCI,
  two OHCIs): `AppleSynopsysOTGDevice::start` finds 7+7 endpoints, the HSIC Wi-Fi and baseband ports time
  out (`device has not connected after 1500ms`, nothing is behind them).
- launchd shuts the system down (`About to call: reboot(RB_AUTOBOOT)`), the kernel prints `pmu restart`
  and writes D1881 register 0x96 <- 0x2b; the PMU model resets the machine and the kernel boots again, about
  every 60 s of wall time (three full cycles in a 200 s run, `runs/n94/m2-serial.log`).

### B1-B2: the PPN NAND (2026-10-17)

```
python tools/ios-prep/ios_prep.py nand --out ../runs/n94/nand
python tools/ios-prep/ios_prep.py kboot ../firmware/n94_10B329 --hide arm-io/ae2 --nand ppn     --add-boot-arg nand-enable-reformat=1
build/qemu-system-arm -M iPhone-4S,kboot=../firmware/n94_10B329/kboot.bin,nand=../runs/n94/nand     -serial file:../runs/n94/m2-root.log -display none -monitor stdio -trace 's5l8940_iop*'
```

The first boot formats the FTL (nine minutes of emulated erases and writes); later boots open it. The
kernel reaches `FTL_Open [OK]`, the 1953125-sector block device and `IOFlashNVRAM::start: nand nvram
started successfully`, then waits for partition 1 of that disk (`hardware.md` "Storage: the PPN mailbox").
NVRAM persists: a restore-ramdisk boot (`--ramdisk restore --nand ppn`, `runs/n94/m2-rd.log`) runs
`/usr/sbin/nvram`, syncs ("committing changes... done"), reboots, and the next start reads the saved
generation back instead of "starting with freshly wiped NVRAM".

### B3: the system volume on the FTL's disk, the real root (2026-10-17)

The FTL's on-flash format is undocumented, so the volume goes in through the guest: one *install boot* on
the IPSW's restore ramdisk with the emulator's helper (`contrib/it-install`, built by `ios-prep install`)
in place of `restored_external`. It writes the system partition as *marker* pages (magic, source, 4 KiB
block) the page store serves from `rootfs.hfs` on the host, the MBR, and makes the data volume
(`hardware.md` "Storage: the install boot"). From the repository root, on a store `ios_prep.py nand` made:

```
python tools/ios-prep/ios_prep.py install ../firmware/n94_10B329 --nand ../runs/n94/nand --out ../runs/n94/install
python tools/ios-prep/ios_prep.py kboot ../firmware/n94_10B329 --nand ppn --hide arm-io/ae2 --ramdisk restore \
    --ramdisk-file ../runs/n94/install/ramdisk-install.dmg --bundle ../runs/n94/install/kboot.bin \
    --add-boot-arg nand-enable-reformat=1
build/qemu-system-arm -M iPhone-4S,kboot=../runs/n94/install/kboot.bin,nand=../runs/n94/nand \
    -serial file:../runs/n94/m2-install.log -display none -monitor stdio
```

`install` needs clang and ld.lld (the MSYS2 UCRT64 ones are found by themselves; `--clang`/`--lld`
otherwise) and builds both helpers, `it_install` and `it_keybag` (B4, below). On a blank store the kernel formats the FTL first (`nand-enable-reformat=1`, nine minutes);
then launchd runs the helper: `it_install: hello`, the 312,445 markers (40 s), `MBR written`, `newfs_hfs`,
`mount_hfs`, `launchd overrides`, `it_install: done`, and the halt (`runs/n94/run-install.sh`, outside
the repository, quits QEMU on that line; the kernel's own halt ends in a panic after `pmu go stdby`, the
D1881 model has no standby yet). A second install boot finds the MBR and only revisits the data volume.

The normal boot is the bundle with no ramdisk, the device tree's `root-matching` (IOMedia, Partition ID 1)
as the A4 boards use it:

```
python tools/ios-prep/ios_prep.py kboot ../firmware/n94_10B329 --nand ppn --hide arm-io/ae2
build/qemu-system-arm -M iPhone-4S,kboot=../firmware/n94_10B329/kboot.bin,nand=../runs/n94/nand -serial stdio -display none
```

What happens (`runs/n94/m2-root.log`, `runs/n94/run-m2.sh`):

- `IOFDiskPartitionScheme` publishes `disk0s1` and `disk0s2` from the MBR; `Got boot device =
  .../AppleSwissPPNFTL/IOFlashBlockDevice/IOBlockStorageDriver/...`, **`BSD root: disk0s1`**, about 20 s
  after power-on (the FTL opens without formatting; the page store answers the catalog reads from
  `rootfs.hfs`).
- launchd runs `fsck_hfs` on both volumes (`QUICKCHECK ONLY; FILESYSTEM CLEAN`) and mounts them as the
  IPSW's fstab says: `/dev/disk0s1 on / (hfs, local, read-only, journaled, noatime)`, `/dev/disk0s2 on
  /private/var (hfs, local, nodev, nosuid, noatime)`.
- The daemons come up from the real system volume: UserEventAgent, notifyd, backboardd, configd, syslogd,
  CommCenter, sandboxd, mediaserverd, lockdownd, wifid, ptpd, iapd, apsd, mobileassetd, securityd,
  SpringBoard's prerequisites; FIPS user-space POST passes. Wi-Fi and the baseband time out on their HSIC
  ports as before, Bluetooth and keybagd are not started (below).
- Two jobs were disabled through launchd's overrides database on the data volume, written by the install
  helper (the system volume is untouched): `com.apple.mobile.keybagd`, which without a system keybag
  prints `FATAL KEYBAG ERROR: kb_load` and reboots into recovery 20 s after launchd (back on since B4,
  below), and `com.apple.BTServer`/`com.apple.BlueTool`, as the fork keeps them off on the A4 boards: with nothing
  behind uart3, BlueTool's HCI traffic through AppleOnboardSerial's rx DMA path ended in a kernel assertion
  (`AppleSimpleUARTSync.cpp:2177`) when uart3 and uart5 were still in the unimplemented window; the
  machine now has the device tree's four UARTs (0, 1, 3, 5).
- The run of 7 minutes ends with launchd and its daemons alive and no reboot: M2.

### B4: effaceable storage and the system keybag (2026-10-17)

What SpringBoard needs beyond launchd: formatted effaceable storage and the system keybag, both made by
`restored_external` on a real restore and both refused outside a trusted root. They are now a step of the
install boot (`hardware.md` "Storage: effaceable storage and the system keybag"): `ios-prep install` also
builds `contrib/it-install/it_keybag.c`, a helper linked against the ramdisk's own dyld (its three
`dlopen`/`dlsym`/`dlerror` imports bound by dyld from libSystem, the rest raw syscalls as in `it_install`),
and stages it on the ramdisk as `/usr/bin/TiSerialFlasher` (an existing file `hfs.py` can replace); the
same `install` + `kboot` + boot commands as B3 above. `it_install` execs it with the data volume mounted at
`/mnt2`, and it calls the IPSW's IOKit and MobileKeyBag as the fork's `contrib/it-keybag` does on the A4
boards: `AppleEffaceableStorage` selectors 3 (isFormatted) and 4 (format), then
`MKBKeyBagCreateSystem(NULL, "/mnt2")`. The console (`runs/n94/m2-install.log`):

```
it_keybag: hello (dyld), console fd 5
[effaceable:INIT] formatting storage
[effaceable:INIT] format succeeded
it_keybag: effaceable open 0x00000000 isFormatted 0x00000000 -> 1
booted from secure root: give device keybag access to everyone
it_keybag: MKBKeyBagCreateSystem -> 0, /mnt2/keybags/systembag.kb 1495 bytes
it_install: system keybag in place, keybagd stays enabled
```

The page store needed nothing new: the format erases and writes the `plog` pool's SLC blocks through the
single-page opcodes, and every later boot reads `[effaceable:INIT] found current generation, 2, in group 1`
instead of `unable to find content`. A second install boot leaves both alone (`systembag.kb present`).
`it_install` now writes launchd's overrides with only the Bluetooth jobs disabled; keybagd is disabled only
when `it_keybag` fails.

The normal boot with keybagd (`runs/n94/m2-root.log`, `run-m2.sh 420`):

- Same path as B3 to the daemons: `BSD root: disk0s1`, both volumes clean and mounted, `launchd[1]` at 5 s,
  CommCenter, mediaserverd, ptpd, iapd, apsd, mobileassetd under their sandbox profiles.
- keybagd runs: `AppleKeyStore:cp_key_store_action(1)` twice at 17 s, the kernel taking the system bag
  (the same two lines the install boot printed when it was created; the B3 run had none), and no `FATAL
  KEYBAG ERROR` and no reboot into recovery. keybagd's own `System Keybag loaded` goes to syslog, not to
  the serial console, so the console's proof is the keystore action plus the uptime.
- backboardd reaches the display stack: `IOMobileFramebufferUserClient::set_hotplug_notify`, the light
  sensor's `preEmptiveSensorStartup`, AppleRGBOUT powered up and down; but `CLCD not initied by iBoot,
  driver will not load` (the kernel's AppleCLCD expects the pipe registers as iBoot leaves them, the same
  gate the A4 display model had to pre-set: `docs/ipad1/ios4.md` "Past the keybag"), so there is no main
  framebuffer and SpringBoard has nothing to draw on. That is M3.
- The USB stack comes up as the PTP + Apple Mobile Device configuration (AppleUSBMux, AppleUSBEthernet
  registered), the baseband's HSIC port times out as before.
- 7 minutes, seven monitor samples `VM status: running`, no panic, no reboot.

Next (after M3, below): M4, the multitouch digitizer on spi1 (no model yet: its nub stays busy, and
Setup cannot be walked), the PMU standby on halt, the data volume's journal.

### M3: Setup Assistant on the panel (2026-10-18)

The first-boot Setup Assistant (the language list, `runs/n94/progress/2026-10-18_M3_setup-assistant.png`)
on the 640x960 panel, 22 minutes of emulated boot after a fresh data volume: the data migration of a first
boot takes about 14 of them (Apple logo and a progress bar, `2026-10-18_M3_migracao-andando.png`), then
SpringBoard launches Setup. Later boots, the migration done, show Setup's welcome screen ("iPhone", slide
to set up) after 4 minutes (`2026-10-18_M3_setup-boas-vindas.png`). From the repository root, on a store `ios_prep.py nand` made (B1-B4 above):

```
python tools/ios-prep/ios_prep.py install ../firmware/n94_10B329 --nand ../runs/n94/nand --out ../runs/n94/install
python tools/ios-prep/ios_prep.py kboot ../firmware/n94_10B329 --nand ppn --hide arm-io/ae2 --ramdisk restore     --ramdisk-file ../runs/n94/install/ramdisk-install.dmg --bundle ../runs/n94/install/kboot.bin     --add-boot-arg nand-enable-reformat=1
build/qemu-system-arm -M iPhone-4S,kboot=../runs/n94/install/kboot.bin,nand=../runs/n94/nand     -serial file:../runs/n94/m2-install.log -display none -monitor stdio      # until "it_install: done"
python tools/ios-prep/ios_prep.py sysvol ../firmware/n94_10B329 --job com.apple.backboardd     --job com.apple.SpringBoard --env CA_ENABLE_OGL=0
python tools/ios-prep/ios_prep.py sysvol ../firmware/n94_10B329 --job com.apple.BTServer     --job com.apple.BlueTool --disable true
python tools/ios-prep/ios_prep.py kboot ../firmware/n94_10B329 --nand ppn
build/qemu-system-arm -M iPhone-4S,kboot=../firmware/n94_10B329/kboot.bin,nand=../runs/n94/nand     -serial file:../runs/n94/m3-serial.log -display sdl -monitor stdio
```

The two `sysvol` edits are now made by `prepare` itself ("Preparing the firmware"), and `device create`
runs the whole sequence ("Virtual devices"). The normal boot no longer hides `arm-io/ae2` (the install
boot still does). `screendump FILE.ppm` in the
monitor saves the panel; `runs/n94/run-m3.sh SECS` (outside the repository) takes one every 30 s. With no
touch the panel goes dark after about two minutes (auto-lock). What it took, in order:

1. **The display** (`hardware.md` "Display: the pipe as iBoot leaves it"): AppleCLCD adopts the framebuffer
   the model leaves as iBoot would, backboardd swaps through the A5 pipe's layer MMU, the model composes UI0
   and UI1 (an MMU-on layer is live at base 0). The first frame was backboardd's boot overlay, the Apple logo
   over an empty progress bar, and it stayed.
2. **Audio.** SpringBoard waited in `BKSDisplayServicesStart` on backboardd, whose CoreAnimation setup
   waited on mediaserverd's Fig server, and mediaserverd sat in `FigPlayerCMSessionOneTimeInitialization`:
   its audio session needs the audio hardware, and on the A5 every route goes through the AE2 coprocessor,
   hidden since M2. `hw/arm/s5l8940_ae2.c` models it high-level (`hardware.md` "The AE2"), and the four I2S
   blocks are the A4 model at the A5's bases (AppleSamsungI2S spun on the drained bit). AppleCS42L63Audio
   and Highland Park start, mediaserverd reaches its run loop, backboardd and SpringBoard go on.
3. **The data volume** (`contrib/it-install/it_install.c`): the migration (DataMigrator's plugins) waited
   on assetsd, which aborted on "Error validating url for store" (CoreData): the photo library's directory
   was missing. The install boot now lays the IPSW's own `/private/var` skeleton on the data volume (58
   folders, small files and the localtime link, with their modes and owners, generated from rootfs.hfs by
   `guest_install.var_skeleton`), as a restore does; the 190 MB of PreinstalledAssets are left out. It also
   writes with content protection off and turns it back on (`kHFSContentProtectionBit`): what it wrote on a
   protected volume (the keybag, launchd's overrides) was unreadable on the next boot, keybagd's kb_load
   failed ("FATAL KEYBAG ERROR", a reboot into recovery). launchd still ignores the overrides database the
   helper writes since the volume is protected, so the Bluetooth jobs are disabled in their plists instead
   (BlueTool's HCI traffic on uart3 ends in AppleSimpleUARTSync's assertion, a kernel panic).
4. **Edits to the system volume** (`sysvol`) reach the guest again: the FTL's garbage collection copies a
   marker page as the bytes it was served, so the pages it had moved no longer followed rootfs.hfs (an edited
   plist read as garbage and launchd dropped the job: mediaserverd vanished after its plist was rewritten).
   Every install boot now writes the markers again ("already installed, refreshing the markers"); an edit
   made long after an install may need one more install boot.

How the guest was read with no user-space console (output to `/dev/console` from user space never reaches
the serial port here): `tools/dev/xnu_procs.py` lists the processes through QEMU's gdbstub (`-s`), the crash
and stackshot reports are plain text in the page store (`runs/n94/nand/ch*-ce0.pages`, `XOR 0xff`; a byte
search for `Incident Identifier:`), and user stacks come from the threads' saved state (10B329: the task's
thread queue at task+0x28, a thread's next at +0x230, its user registers at +0x240, map+0x2c the pmap whose
second word is the physical L1 table), symbolized from the shared cache's export tables with the boot's
slide (`mach_msg_trap`'s return address). A gdbstub breakpoint on `objc_exception_throw` caught assetsd's
exception.

### Activation: lockdownd's short-circuit (2026-10-18)

An emulated unit has no Apple-issued activation record (those are bound to a real unit's identity), so
Setup's activation page needs lockdownd to report Activated on its own. On 10B329 the seeded data ark
(`install --activation factory`) does not suffice. `dealwith_activation` (0xf1bc in lockdownd, sha256
04d029e7...) sets `ActivationState = Activated` only through a development short-circuit: unless the ark
sets `DisableHactivation`, it calls a predicate (`bl 0x1bca0; cmp r0, #1; beq.w`) and on 1 logs "Short
circuiting activation state to Activated." Otherwise it looks for a record (POD, DEFAULT, UNLOCK, CARE_FLAG,
ICCID, WILDCARD) and ends in "Could not find an activation record". This matches the iPod 4's 6.x
(docs/n81/README.md): the data ark held up to 10A523, and from 10B144 on a binary pattern was needed.

`tools/ios-prep/lockdownd_patch.py` makes the short-circuit unconditional. The predicate's `bl` becomes
`movs r0, #1` twice, and the `bne` past the DisableHactivation log becomes a `b` to the predicate. Both
sites are found by shape and by the CFStrings their blocks log. Each must match exactly once or nothing is
written, so the patch refuses other binaries and a second run finds the file already patched. The code
signature's SHA-1 page hash is recomputed (AMFI is off here, so this only keeps the signature
self-consistent). The result (sha256 f9287c33...) is byte-identical to Legacy-iOS-Kit's hacktivation patch
for this build (`Down_iPhone2,1_6.1.3_10B329.bundle/lockdownd.patch`, a bspatch that kit applies through
SSH on a jailbroken device). That kit is the cross-check only; the emulator writes its system volume
directly and needs no jailbreak.

`ios_prep.py prepare` applies it by default, right after the rootfs is expanded. The system volume is
per firmware, so every virtual unit made from that IPSW gets it, and a re-run finds it already done
(`hashes.json` "activation" records the outcome; `--stock-lockdownd` leaves the IPSW's binary). On a
lockdownd the patcher does not recognize, `prepare` logs why and goes on with the stock binary. A
firmware directory prepared before this takes it with:

```
python tools/ios-prep/ios_prep.py sysvol ../firmware/n94_10B329 --activation-shortcut
```

The binary goes in uncompressed in place of its decmpfs copy (143 blocks from the donor, as `sysvol`'s
plists do). Then an install boot refreshes the markers, as for any `sysvol` edit, followed by the normal boot.

The result, shown by Setup since the NAND page store has no plaintext data ark to read back (no
`ActivationState` string in either channel, raw or XOR):

- With the stock lockdownd and the FactoryActivated ark, Setup stopped at its activation page, "Conecte ao
  iTunes" (`runs/n94/progress/2026-10-18_activation_antes-conecte-itunes.png`).
- With the patched lockdownd, after the install boot and a normal boot, Setup goes from language, country
  and Location Services straight to "Configuração" (set up as a new iPhone), then Apple ID (skipped),
  "Termos e Condições" (accepted), Diagnóstico ("Não Enviar") and "Obrigado!", to the home screen
  (`2026-10-18_activation_depois-configuracao.png`, `2026-10-18_M4_tela-inicial.png`). No activation
  page. Ajustes opens (Wi-Fi inactive, Bluetooth unavailable: those jobs are off). The power button locks,
  and the lock screen's slider unlocks back to the home screen (`2026-10-18_M4_tela-bloqueio.png`).

Walking it with `tools/dev/n94_input.py`: the welcome slider counts only while the panel is lit after a
wake, which lasts under 10 s with no input, so the swipe goes right after the Home press: `key home ; wait
1.5 ; swipe 105 862 610 862`. The Apple ID step's spinner waits about 90 s for the network before the
Terms show.

### State at M1 (2026-10-17, `runs/n94/m1-serial.log`)

The machine (`hw/arm/n94.c`) has one Cortex-A9, 512 MiB at 0x80000000 (its first page aliased at PA 0),
the AIC (`hw/arm/s5l8940_aic.c`, register map in `hardware.md`), the A4 PMGR and GPIO models at the A5
addresses, QEMU's `l2x0` for the PL310 and the two Samsung UARTs; everything else in 0x30000000-0x3FFFFFFF
is an unimplemented-device window. What the kernel does with it:

- The serial console comes up in `PE_init_iokit`: the first bytes on uart0 are `iBoot version:
  iBoot-1537.9.55`. The `Darwin Kernel Version 13.0.0 ... RELEASE_ARM_S5L8940X` banner is printed before
  that and goes only to the kernel's message buffer (`pmemsave` of DRAM finds the copy at 0x8146dee0 next to
  the `version` string itself at 0x802cfbec); `-v` does not change that, so it never reaches the UART.
- corecrypto's FIPS tests, AMFI (disabled by the boot-args), `AppleS5L8940XIO` (chip revision B0),
  backlight, `AppleInterruptController` (`_aicVersion = 0 _aicNumExtInts = 0xc0 _aicNumIPIs = 4`), GPIO,
  the performance controller's tables, PL310, spi1, the three I2C controllers, MIPI-DSI, DisplayPort, the
  I2S controllers, both scalers, VXE, the camera (`AppleH4CamIn::start`) all start without faults.
- The clock runs: the rtclock's deadline FIQs are acked and re-armed (about 20,000 in 150 s), so IOKit
  matching proceeds on the scheduler. The A5 PMGR has clock registers the A4 model does not know (listed in
  `hardware.md`); they read as zero and nothing complains yet.
- `AppleARMPE::getGMTTimeOfDay can not provide time of day RTC did not show up` (no PMU on i2c0), then
  `Waiting on <dict ...IOMedia... Partition ID 0x1>`, AppleCLCD and RGBOUT start, and the kernel sits at
  `Still waiting for root device`: M2 is the NAND (the IOP's FMI path or a PPN model) and the PMU.
