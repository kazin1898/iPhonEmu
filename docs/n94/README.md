# iPhone 4S (n94ap, A5 / S5L8940X): `-M iPhone-4S`

The project's target board: iOS 6.1.3 (10B329) on the A5, booted from a kernel bundle (kboot) with no
boot ROM or iBoot, as the A4 boards in `hw/arm/ipad1.c` are. The hardware as the IPSW describes it is
in `hardware.md`; the raw inventory (`devicetree.txt`, `iomap.tsv`, `kexts.txt`) is regenerated by
`ios-prep`.

## Preparing the firmware

Apple's `iPhone4,1_6.1.3_10B329_Restore.ipsw` (SHA-256 601d5112...56d2, 965,016,471 bytes) and the
keys on The Apple Wiki (`Keys:BrightonMaps_10B329_(iPhone4,1)`; `ios-prep` fetches them, or pass
`--keys`). From the repository root, with Python 3 and `cryptography`:

```
python tools/ios-prep/ios_prep.py prepare ../firmware/iPhone4,1_6.1.3_10B329_Restore.ipsw \
    --out ../firmware/n94_10B329 --docs docs/n94
```

Output (`hashes.json` records every SHA-256):

| File | What | Check |
|---|---|---|
| `kernelcache.mach` | 14,053,376 B | `feedface`, armv7, `xnu-2107.7.55.2.2~1/RELEASE_ARM_S5L8940X`, Adler-32 of the complzss verified |
| `DeviceTree.bin` | 78,520 B | first property `compatible` = `N94AP`, `iPhone4,1`, `AppleARM`; 101 nodes |
| `iBoot.bin`, `LLB.bin`, `AppleLogo.bin` | decrypted stages and the boot logo | `iBoot-1537.9.55` string, `iBootIm` header |
| `rootfs.hfs` | 1,279,774,720 B | HFSX (`HX`) volume header at 0x400, journaled |
| `kboot.bin` | 14,405,656 B | `K48KBOOT` trailer: load 0x80000000, entry 0x800860c8, boot_args 0x80DBC000 |
| `identity.json` | the synthesized unit (serial, MLB, ECID, MACs), seeded | reproducible with `--seed` |

What the bundle holds (`kboot.json`): the kernel's segments at their link addresses (VA == PA on the
A5 with no slide), the filled device tree at 0x80DA8000 and a boot_args page at 0x80DBC000 with
**Version 18**, which is what this kernel's `pe_identify_machine` compares against (the A4 6.x
kernels want 3; `ios-prep` reads the value off each kernel). `memSize` is 512 MiB minus vram and
pram, `topOfKernelData` 0x80DBD000 rounded to 16 KiB. The device tree gets the iBoot fills the A4
boards get (identity, flags, clocks, memory map, sgx unmatched, test IMEI; the NVRAM proxy image only
without `--nand ppn`, since with the NVRAM on the NAND the kernel must read it from IOFlashNVRAM) plus:

- `--cpus 1` (default for bring-up): `cpus/cpu1` is unmatched (`device_type off`, name `xcpu`).
- `--nand raw` (default): the A4 raw-NAND geometry and `ppn-device 0`; `--nand ppn` keeps PPN.
- `--hide NODE` unmatches any further node; `--verbose-boot` appends `-v`.
- `--ramdisk restore|update` (with `--ipsw` once, to decrypt it) stages the IPSW's ramdisk after boot_args,
  under topOfKernelData, publishes it as `chosen/memory-map/RAMDisk` and adds `rd=md0`: the kernel's md
  driver makes it the root, as iBoot does for a restore. That is how M2 was reached without a NAND model.
- `--cpus 1` also puts `cpus=1` in the boot-args: AppleARMPE counts every child of `/cpus` (the hidden
  cpu1 included) for the CPU interrupt controller and only that boot-arg lowers the count; with 2 expected,
  `AppleInterruptController::start` blocks in `IOCPUInterruptController::registerInterrupt` forever and no
  device interrupt is ever unmasked.

## Booting

From the repository root (the Windows build is `build/qemu-system-arm.exe`, run from the MSYS2 UCRT64
shell so its DLLs resolve):

```
build/qemu-system-arm -M iPhone-4S,kboot=../firmware/n94_10B329/kboot.bin -serial stdio -display none \
    -d unimp,guest_errors -D ../runs/n94/m1.log
```

`-trace 's5l8940_aic*'` logs every AIC access (the timer and FIQ included). For a bounded run whose
qemu log is flushed, quit through the monitor instead of killing the process:
`(sleep 150; echo quit) | build/qemu-system-arm ... -serial file:../runs/n94/m1-serial.log -monitor stdio`
(`runs/n94/run-m1.sh`, outside the repository, does this). Note that `-trace file=` also receives the
`-d` log output.

### M2: launchd from the restore ramdisk (2026-10-17, `runs/n94/m2-serial.log`)

```
python tools/ios-prep/ios_prep.py kboot ../firmware/n94_10B329 --ramdisk restore \
    --ipsw ../firmware/iPhone4,1_6.1.3_10B329_Restore.ipsw --hide arm-io/iop --hide arm-io/ae2
build/qemu-system-arm -M iPhone-4S,kboot=../firmware/n94_10B329/kboot.bin -serial stdio -display none
```

The two IOP nodes are hidden because `AppleA5IOP` and `A5AE2` load their EmbeddedIOP firmware and wait for
the coprocessor forever (the IOP core model is M3 work with the NAND). What happens, in order:

- `AppleInterruptController` registers (it needs `cpus=1`, above), so drivers get their interrupts: the
  watchdog, the serial ports, the light sensor, DWI, the CDMA with its AES filter.
- `CDMAAES` starts the `IOAESAccelerator`, which asks the platform for `SecureRoot`; AppleARMPE answers once
  bsd_init has named the root (`secure-root-prefix` is `md`, so `md0` is secure) and that handshake is what
  releases `IOSecureBSDRoot` in bsd_init. Without the CDMA the kernel sat forever after `BSD root: md0`.
- The PMU driver finds the D1881 on i2c0 (events, ADC, RTC counter and restart modeled; the ADC reads
  mid-scale on every channel), the compass and accelerometer start, the gyro fails its calibration check;
  `BSD root: md0`. restored's log carries the host's date.
- `launchd[1] has started up`; `restored_external` runs, finds no display service and no USB host
  (`enable_usb_connections failed`), waits in vain for the `IONVRAM` resource (the NVRAM lives in the NAND's
  partitions on this board) and exits asking for a reboot.
- The USB stack comes up on the A4 models (PHY, Synopsys OTG in device mode with its built-in host, EHCI,
  two OHCIs): `AppleSynopsysOTGDevice::start` finds 7+7 endpoints, the HSIC Wi-Fi and baseband ports time
  out (`device has not connected after 1500ms`, nothing is behind them).
- launchd shuts the system down (`About to call: reboot(RB_AUTOBOOT)`), the kernel prints `pmu restart`
  and writes D1881 register 0x96 <- 0x2b; the PMU model resets the machine and the kernel boots again, about
  every 60 s of wall time (three full cycles in a 200 s run, `runs/n94/m2-serial.log`).

### B1-B2: the PPN NAND (2026-10-17)

```
python tools/ios-prep/ios_prep.py nand --out ../runs/n94/nand
python tools/ios-prep/ios_prep.py kboot ../firmware/n94_10B329 --hide arm-io/ae2 --nand ppn     --add-boot-arg nand-enable-reformat=1
build/qemu-system-arm -M iPhone-4S,kboot=../firmware/n94_10B329/kboot.bin,nand=../runs/n94/nand     -serial file:../runs/n94/m2-root.log -display none -monitor stdio -trace 's5l8940_iop*'
```

The first boot formats the FTL (nine minutes of emulated erases and writes); later boots open it. The
kernel reaches `FTL_Open [OK]`, the 1953125-sector block device and `IOFlashNVRAM::start: nand nvram
started successfully`, then waits for partition 1 of that disk (`hardware.md` "Storage: the PPN mailbox").
NVRAM persists: a restore-ramdisk boot (`--ramdisk restore --nand ppn`, `runs/n94/m2-rd.log`) runs
`/usr/sbin/nvram`, syncs ("committing changes... done"), reboots, and the next start reads the saved
generation back instead of "starting with freshly wiped NVRAM".

### B3: the system volume on the FTL's disk, the real root (2026-10-17)

The FTL's on-flash format is undocumented, so the volume goes in through the guest: one *install boot* on
the IPSW's restore ramdisk with the emulator's helper (`contrib/it-install`, built by `ios-prep install`)
in place of `restored_external`. It writes the system partition as *marker* pages (magic, source, 4 KiB
block) the page store serves from `rootfs.hfs` on the host, the MBR, and makes the data volume
(`hardware.md` "Storage: the install boot"). From the repository root, on a store `ios_prep.py nand` made:

```
python tools/ios-prep/ios_prep.py install ../firmware/n94_10B329 --nand ../runs/n94/nand --out ../runs/n94/install
python tools/ios-prep/ios_prep.py kboot ../firmware/n94_10B329 --nand ppn --hide arm-io/ae2 --ramdisk restore \
    --ramdisk-file ../runs/n94/install/ramdisk-install.dmg --bundle ../runs/n94/install/kboot.bin \
    --add-boot-arg nand-enable-reformat=1
build/qemu-system-arm -M iPhone-4S,kboot=../runs/n94/install/kboot.bin,nand=../runs/n94/nand \
    -serial file:../runs/n94/m2-install.log -display none -monitor stdio
```

`install` needs clang and ld.lld (the MSYS2 UCRT64 ones are found by themselves; `--clang`/`--lld`
otherwise) and builds both helpers, `it_install` and `it_keybag` (B4, below). On a blank store the kernel formats the FTL first (`nand-enable-reformat=1`, nine minutes);
then launchd runs the helper: `it_install: hello`, the 312,445 markers (40 s), `MBR written`, `newfs_hfs`,
`mount_hfs`, `launchd overrides`, `it_install: done`, and the halt (`runs/n94/run-install.sh`, outside
the repository, quits QEMU on that line; the kernel's own halt ends in a panic after `pmu go stdby`, the
D1881 model has no standby yet). A second install boot finds the MBR and only revisits the data volume.

The normal boot is the bundle with no ramdisk, the device tree's `root-matching` (IOMedia, Partition ID 1)
as the A4 boards use it:

```
python tools/ios-prep/ios_prep.py kboot ../firmware/n94_10B329 --nand ppn --hide arm-io/ae2
build/qemu-system-arm -M iPhone-4S,kboot=../firmware/n94_10B329/kboot.bin,nand=../runs/n94/nand -serial stdio -display none
```

What happens (`runs/n94/m2-root.log`, `runs/n94/run-m2.sh`):

- `IOFDiskPartitionScheme` publishes `disk0s1` and `disk0s2` from the MBR; `Got boot device =
  .../AppleSwissPPNFTL/IOFlashBlockDevice/IOBlockStorageDriver/...`, **`BSD root: disk0s1`**, about 20 s
  after power-on (the FTL opens without formatting; the page store answers the catalog reads from
  `rootfs.hfs`).
- launchd runs `fsck_hfs` on both volumes (`QUICKCHECK ONLY; FILESYSTEM CLEAN`) and mounts them as the
  IPSW's fstab says: `/dev/disk0s1 on / (hfs, local, read-only, journaled, noatime)`, `/dev/disk0s2 on
  /private/var (hfs, local, nodev, nosuid, noatime)`.
- The daemons come up from the real system volume: UserEventAgent, notifyd, backboardd, configd, syslogd,
  CommCenter, sandboxd, mediaserverd, lockdownd, wifid, ptpd, iapd, apsd, mobileassetd, securityd,
  SpringBoard's prerequisites; FIPS user-space POST passes. Wi-Fi and the baseband time out on their HSIC
  ports as before, Bluetooth and keybagd are not started (below).
- Two jobs were disabled through launchd's overrides database on the data volume, written by the install
  helper (the system volume is untouched): `com.apple.mobile.keybagd`, which without a system keybag
  prints `FATAL KEYBAG ERROR: kb_load` and reboots into recovery 20 s after launchd (back on since B4,
  below), and `com.apple.BTServer`/`com.apple.BlueTool`, as the fork keeps them off on the A4 boards: with nothing
  behind uart3, BlueTool's HCI traffic through AppleOnboardSerial's rx DMA path ended in a kernel assertion
  (`AppleSimpleUARTSync.cpp:2177`) when uart3 and uart5 were still in the unimplemented window; the
  machine now has the device tree's four UARTs (0, 1, 3, 5).
- The run of 7 minutes ends with launchd and its daemons alive and no reboot: M2.

### B4: effaceable storage and the system keybag (2026-10-17)

What SpringBoard needs beyond launchd: formatted effaceable storage and the system keybag, both made by
`restored_external` on a real restore and both refused outside a trusted root. They are now a step of the
install boot (`hardware.md` "Storage: effaceable storage and the system keybag"): `ios-prep install` also
builds `contrib/it-install/it_keybag.c`, a helper linked against the ramdisk's own dyld (its three
`dlopen`/`dlsym`/`dlerror` imports bound by dyld from libSystem, the rest raw syscalls as in `it_install`),
and stages it on the ramdisk as `/usr/bin/TiSerialFlasher` (an existing file `hfs.py` can replace); the
same `install` + `kboot` + boot commands as B3 above. `it_install` execs it with the data volume mounted at
`/mnt2`, and it calls the IPSW's IOKit and MobileKeyBag as the fork's `contrib/it-keybag` does on the A4
boards: `AppleEffaceableStorage` selectors 3 (isFormatted) and 4 (format), then
`MKBKeyBagCreateSystem(NULL, "/mnt2")`. The console (`runs/n94/m2-install.log`):

```
it_keybag: hello (dyld), console fd 5
[effaceable:INIT] formatting storage
[effaceable:INIT] format succeeded
it_keybag: effaceable open 0x00000000 isFormatted 0x00000000 -> 1
booted from secure root: give device keybag access to everyone
it_keybag: MKBKeyBagCreateSystem -> 0, /mnt2/keybags/systembag.kb 1495 bytes
it_install: system keybag in place, keybagd stays enabled
```

The page store needed nothing new: the format erases and writes the `plog` pool's SLC blocks through the
single-page opcodes, and every later boot reads `[effaceable:INIT] found current generation, 2, in group 1`
instead of `unable to find content`. A second install boot leaves both alone (`systembag.kb present`).
`it_install` now writes launchd's overrides with only the Bluetooth jobs disabled; keybagd is disabled only
when `it_keybag` fails.

The normal boot with keybagd (`runs/n94/m2-root.log`, `run-m2.sh 420`):

- Same path as B3 to the daemons: `BSD root: disk0s1`, both volumes clean and mounted, `launchd[1]` at 5 s,
  CommCenter, mediaserverd, ptpd, iapd, apsd, mobileassetd under their sandbox profiles.
- keybagd runs: `AppleKeyStore:cp_key_store_action(1)` twice at 17 s, the kernel taking the system bag
  (the same two lines the install boot printed when it was created; the B3 run had none), and no `FATAL
  KEYBAG ERROR` and no reboot into recovery. keybagd's own `System Keybag loaded` goes to syslog, not to
  the serial console, so the console's proof is the keystore action plus the uptime.
- backboardd reaches the display stack: `IOMobileFramebufferUserClient::set_hotplug_notify`, the light
  sensor's `preEmptiveSensorStartup`, AppleRGBOUT powered up and down; but `CLCD not initied by iBoot,
  driver will not load` (the kernel's AppleCLCD expects the pipe registers as iBoot leaves them, the same
  gate the A4 display model had to pre-set: `docs/ipad1/ios4.md` "Past the keybag"), so there is no main
  framebuffer and SpringBoard has nothing to draw on. That is M3.
- The USB stack comes up as the PTP + Apple Mobile Device configuration (AppleUSBMux, AppleUSBEthernet
  registered), the baseband's HSIC port times out as before.
- 7 minutes, seven monitor samples `VM status: running`, no panic, no reboot.

Next: M3 (the panel: AppleCLCD/MIPI-DSI with a framebuffer the display pipe draws, so backboardd and
SpringBoard have a screen), the PMU standby on halt, the data volume's journal.

### State at M1 (2026-10-17, `runs/n94/m1-serial.log`)

The machine (`hw/arm/n94.c`) has one Cortex-A9, 512 MiB at 0x80000000 (its first page aliased at PA 0),
the AIC (`hw/arm/s5l8940_aic.c`, register map in `hardware.md`), the A4 PMGR and GPIO models at the A5
addresses, QEMU's `l2x0` for the PL310 and the two Samsung UARTs; everything else in 0x30000000-0x3FFFFFFF
is an unimplemented-device window. What the kernel does with it:

- The serial console comes up in `PE_init_iokit`: the first bytes on uart0 are `iBoot version:
  iBoot-1537.9.55`. The `Darwin Kernel Version 13.0.0 ... RELEASE_ARM_S5L8940X` banner is printed before
  that and goes only to the kernel's message buffer (`pmemsave` of DRAM finds the copy at 0x8146dee0 next to
  the `version` string itself at 0x802cfbec); `-v` does not change that, so it never reaches the UART.
- corecrypto's FIPS tests, AMFI (disabled by the boot-args), `AppleS5L8940XIO` (chip revision B0),
  backlight, `AppleInterruptController` (`_aicVersion = 0 _aicNumExtInts = 0xc0 _aicNumIPIs = 4`), GPIO,
  the performance controller's tables, PL310, spi1, the three I2C controllers, MIPI-DSI, DisplayPort, the
  I2S controllers, both scalers, VXE, the camera (`AppleH4CamIn::start`) all start without faults.
- The clock runs: the rtclock's deadline FIQs are acked and re-armed (about 20,000 in 150 s), so IOKit
  matching proceeds on the scheduler. The A5 PMGR has clock registers the A4 model does not know (listed in
  `hardware.md`); they read as zero and nothing complains yet.
- `AppleARMPE::getGMTTimeOfDay can not provide time of day RTC did not show up` (no PMU on i2c0), then
  `Waiting on <dict ...IOMedia... Partition ID 0x1>`, AppleCLCD and RGBOUT start, and the kernel sits at
  `Still waiting for root device`: M2 is the NAND (the IOP's FMI path or a PPN model) and the PMU.
